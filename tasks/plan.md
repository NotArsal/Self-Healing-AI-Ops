# Implementation Plan: F-DEBT (Remediation Debt)

## Overview
Implement remediation debt tracking and repayment. When a repair successfully restores availability but degrades quality (`MITIGATED` outcome), the system tracks an obligation to revert the repair once the primary system recovers. We will build a persistent database table for this debt, a background checker loop, and the safe repayment execution path.

## Architecture Decisions
- **Debt Tracking**: We will create a `remediation_debt` table via Alembic.
- **Background Checker**: We will use a native `asyncio.create_task` background loop attached to the FastAPI application lifespan, avoiding heavy external dependencies like Celery.
- **Trigger Evaluation**: For v1, the trigger logic for F01 ("llm_proxy healthy for 600s") will be a specific hardcoded Prometheus metric check inside the loop.
- **Repayment Path**: Repayments will reuse the existing executor and `safety.engine.permit()` mechanisms to ensure they are never privileged.

## Task List

### Phase 1: Foundation (Database & Lifespan Task)
- [ ] Task 1: Create Alembic migration and SQLAlchemy model for `remediation_debt` table.
- [ ] Task 2: Setup FastAPI lifespan background task loop in `kavach/api/main.py` that periodically queries `PENDING` debt.

### Checkpoint: Foundation
- [ ] Database migration runs successfully.
- [ ] API starts cleanly and logs background loop heartbeat.

### Phase 2: Debt Creation
- [ ] Task 3: Update `execute_node` (or `verify_node`) to insert a `PENDING` debt record when the `F01` incident outcome evaluates to `MITIGATED`.
- [ ] Task 4: Add Pydantic models for Debt API responses.

### Checkpoint: Debt Creation
- [ ] Injecting F01 and successfully mitigating it creates a row in the `remediation_debt` table.

### Phase 3: Trigger Evaluation & Repayment
- [ ] Task 5: Implement Prometheus trigger evaluator (`gen_ai_error_rate` check) inside the background loop.
- [ ] Task 6: Hook repayment execution to `safety.engine.permit()` and the executor, updating the incident to `RESOLVED` on success, or `ESCALATED` on `max_age_s` expiry.

### Checkpoint: Complete

## Risks and Mitigations
| Risk | Impact | Mitigation |
|------|--------|------------|
| Unbounded background loops block FastAPI | Med | Use `asyncio.sleep` and ensure database calls use the `async_sessionmaker`. |
| Repayment runs destructively | High | Route repayment through the exact same TNR gate (`permit()`) and verification steps as normal repairs. |

# Implementation Plan: F-MEM (Incident Knowledge Base)

## Overview
Implement an incident knowledge base with vector similarity retrieval. We will store successfully resolved incidents (and failed hypotheses) in Postgres using `pgvector`. New incidents will query this memory bank using embeddings generated by `nomic-embed-text` to provide contextual evidence during root cause analysis.

## Architecture Decisions
- **Storage**: `incident_memory` table with a `vector` column (via pgvector).
- **Embeddings**: We will use the existing `nomic-embed-text` model via Ollama.
- **Graph Integration**: 
  - `diagnose_node` will trigger a similarity search and append the results as `Evidence`.
  - The final node (e.g., `verify_node` on success) will save the incident summary and successful repair to the knowledge base.

# Implementation Plan: F-ROLE (Role-Based Fault Applicability)

## Overview
Filter the fault catalogue based on the roles declared by the target application in its `kavach.yaml`. If an application does not declare a `vector_store` role, faults like `F06` (Retrieval Collapse) should not be considered during diagnosis and should be reported as unsupported during onboarding.

## Architecture Decisions
- **Role Extraction**: Parse `kavach.yaml` to extract a set of active roles.
- **Catalogue Filtering**: Modify `kavach/catalogue/loader.py` to filter `FaultDef`s based on `applies_to_roles`.
- **Preflight Reporting**: Update `kavach/preflight/checker.py` to report which faults are excluded.

# Implementation Plan: F-UNK (Unknown-failure hypothesis loop)

## Overview
Handle "Unknown Failure" gracefully by ensuring that if `diagnose_node` returns `INSUFFICIENT_EVIDENCE` or a low confidence, the system immediately escalates and aborts the repair loop.

## Architecture Decisions
- **Plan Node**: Ensure that if `fault_class` is `INSUFFICIENT_EVIDENCE`, `plan_node` yields an empty plan.
- **Outcome Node**: Ensure `outcome_node` sets the final outcome to `ESCALATED` for unknown failures.

### Phase 2: Testing

# Implementation Plan: F-SBX (Sandbox for MEDIUM-risk repairs)

## Overview
Introduce a `SANDBOX` execution loop in the state graph. For faults with `MEDIUM` risk, the repair must first be executed in a sandboxed environment and verified. If sandbox verification fails, it escalates. Only if it passes does it proceed to real execution.

## Architecture Decisions
- **Plan Node**: Tag the state with `sandbox_required = True` if the chosen fault's risk tier is `MEDIUM`.
- **Graph Updates**: Add a `sandbox_execute_node` and `sandbox_verify_node`. Route from `gate` to `sandbox_execute` if `sandbox_required` is true, otherwise straight to `execute`.
- **Sandbox Nodes**: These will run the execution adapter but with an indicator that it is a sandbox (or effectively a dry run if a true sandbox isn't configured).

## Task List

### Phase 1: Core Logic
- [ ] Task 19: Update `IncidentState` in `kavach/graph/state.py` to include `sandbox_required`, `sandbox_passed`, etc.
- [ ] Task 20: Update `plan_node` in `kavach/graph/nodes.py` to check risk and set `sandbox_required`.

### Phase 2: Graph Integration
- [ ] Task 21: Implement `sandbox_execute_node` and `sandbox_verify_node` in `kavach/graph/nodes.py`.
- [ ] Task 22: Update the routing logic in `kavach/graph/workflow.py` to include the sandbox loop.

### Phase 3: Testing
- [ ] Task 23: Write an integration test for `MEDIUM` risk faults to ensure the sandbox loop is exercised.
